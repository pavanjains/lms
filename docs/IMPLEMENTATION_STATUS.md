## Production-readiness work (PROD-01 to PROD-09; added 2026-11-27)
The production-readiness list (PROD-01 to PROD-14) is in docs/TICKETS.md. Merged so far, with head SHAs, check run ids, failure history and open items kept in that ledger:

- PROD-01 (PR #17, 13b00db): production settings now read the invitation settings. Instructor onboarding is off by default in production; when switched on, startup fails unless LMS_PUBLIC_ORIGIN is an HTTPS origin and LMS_INVITATION_FROM_EMAIL is a valid address. Real mail delivery (PROD-05) and HTTPS and proxy headers (PROD-04) are not covered, so onboarding must not be enabled in production yet.
- PROD-06 (PR #19, 71fe4f0): sign-in throttling for students and staff in a new LoginThrottle table (accounts migration 0004_loginthrottle). Fifteen failed attempts in 15 minutes lock the submitted name for 15 minutes; names are stored only as digests; a student credential reset clears that student's lock. No per-IP limit, no staff lock reset, one-time-code step unchanged.
- PROD-07 (PR #21, de5f392): first slice of the audit trail in a new AuditEvent table (accounts migration 0005_auditevent). Events cover sign-in success, first failure in a window, lockout, credential resets, student creation and enrollment changes. Owner-only page at /staff/owner/audit/; the purge_audit_events command deletes events older than LMS_AUDIT_RETENTION_DAYS (default 90) and nothing schedules it yet. Assignment, progress, invitation and instructor-assignment events are not recorded.
- PROD-09 (PR #23, 4f552c9): tests and documentation only, no application code. apps/lessons/test_assignment_concurrency.py holds six PostgreSQL ordered-race tests and two replay tests. Duplicate active assignments were already prevented by the unique constraint and row locks. The review token is not recorded as used in the database, so a concurrent stale session write could make it reusable for up to 900 seconds; that window is documented in docs/ASSIGNMENTS.md and is not closed. Closing it would need a new lessons migration and is an open owner decision.

Verification and migrations: the author could not run the Django tests for these changes; CI and owner-supplied logs are the evidence and are recorded per ticket in TICKETS.md, with earlier failing totals preserved and never reused as passing totals. Accounts migrations 0004 and 0005 are applied and checked only on the owner's local PostgreSQL database; no intended or hosted database has been migrated (PROD-03). Owner-reported browser checks: PROD-07 audit page (2026-11-26) and PROD-02 round 1, all five rows PASS (2026-11-27); neither was independently observed. PROD-02 rounds 2 to 4 and the HTTPS case are not done. No production approval.
